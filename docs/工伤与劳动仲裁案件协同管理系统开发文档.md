## 1. 引言

### 1.1 编写目的

本文档依据《系统定位》文件及本地化部署要求，对“工伤与劳动仲裁案件协同管理系统”进行开发层面设计，明确系统需求、架构、模块、数据模型、接口、安全、本地部署及实施计划，作为后续设计、开发、测试、本地部署和验收的依据。

### 1.2 项目范围

本系统为企业内部案件协同管理平台，部署于企业本地服务器或内网环境，覆盖工伤案件、劳动仲裁案件及关联争议案件的全生命周期管理，实现案件统一建档、状态跟踪、跨部门协同、文档管理、期限预警、报表分析和审计留痕。核心功能不依赖公有云服务。

### 1.3 术语定义

| 术语         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| 工伤案件     | 员工在工作过程中发生伤害，按法定程序进行工伤认定、鉴定、待遇处理等案件 |
| 劳动仲裁案件 | 企业与员工之间因劳动关系产生的争议，提交劳动仲裁委员会处理的案件 |
| 关联争议 | 不再单独建档，通过「争议关联」把两件已有案件关联管理（`case_relation`） |
| 闭环管理     | 登记→分派→办理→审批→预警→结案→归档→分析的全流程管理          |
| RBAC         | 基于角色的访问控制                                           |
| 工作流       | 本系统指自研状态机与节点定义，不依赖外部 BPMN 引擎           |
| 本地化部署   | 系统部署在企业自有服务器或内网环境，数据不出内网，外部集成可选 |
| 可选组件     | Redis、Elasticsearch、RabbitMQ、MinIO、IM/OA/HR 集成等，可按资源与需求启用或关闭 |

## 2. 项目概述

### 2.1 建设背景

企业当前工伤和劳动仲裁案件分散管理，缺乏统一入口和流程约束，跨部门协同效率低，期限预警缺失，文档版本混乱，审计追溯困难。为提升案件管理规范化、协同化和数字化水平，建设本系统，并要求系统可在本地服务器部署运行。

### 2.2 建设原则

1. **统一入口**：所有工伤和仲裁案件统一平台登记、办理、归档。
2. **流程可控**：关键状态变更、审批、会签、结案均有规则约束。
3. **本地可控**：核心业务、数据、文档、日志均存储在本地或内网，外部集成可配置开关。
4. **最小依赖**：默认仅依赖 MySQL 与本地文件存储即可运行，Redis/ES/MQ/MinIO 等按需启用。

### 2.3 总体目标

建设一套覆盖工伤案件和劳动仲裁案件全生命周期的内部协同管理系统，实现案件“登记—分派—办理—审批—预警—结案—归档—分析”的闭环管理，并支持本地化部署、内网访问、本地备份与恢复。

### 2.4 系统架构总览

系统按中心能力划分为五大中心：

| 中心     | 主要能力                                          |
| -------- | ------------------------------------------------- |
| 案件中心 | 建档、状态、关联、结案归档                        |
| 协同中心 | 任务分派、待办、会签                              |
| 文档中心 | 证据材料、版本管理、权限控制、受控下载            |
| 期限中心 | 法定/内部节点提醒、超期预警                       |
| 报表中心 | 案件量、状态分布、协同效率、赔付/裁决金额、超期率；工伤统计表导出 |
| 台账与归档 | 工伤/仲裁统一台账、字段配置、卷宗归档检索      |

## 3. 技术架构

### 3.1 总体技术架构

本地部署优先采用前后端分离、模块化单体架构，支持 Web 管理端与移动端 H5；外部 IM/OA/HR 集成通过适配器与配置开关接入。后期可按需拆分微服务。

```text
┌─────────────────────────────────────────────────────────┐
│ 前端层：Web管理端（Vue 3 + Element Plus） + 移动端H5     │
│         由本地Nginx提供静态资源与反向代理                 │
├─────────────────────────────────────────────────────────┤
│ 接入层：本地Nginx、JWT认证鉴权、限流、HTTPS              │
├─────────────────────────────────────────────────────────┤
│ 应用层：模块化单体（案件/协同/文档/期限/报表/系统管理）  │
│         RBAC、自研状态机、审计日志、本地任务调度          │
├─────────────────────────────────────────────────────────┤
│ 集成层：本地适配器（HR导入、OA可选、IM可选、SMTP邮件）    │
├─────────────────────────────────────────────────────────┤
│ 数据层：MySQL 8.0、本地磁盘（对象存储/缓存/检索均未启用）  │
│         案件主数据、流程数据、文档元数据、审计日志        │
└─────────────────────────────────────────────────────────┘
```

## 4. 功能需求

### 4.1 案件中心

#### 4.1.1 案件建档

- 支持工伤、劳动仲裁两类建档，按类型动态渲染扩展字段；新建时可选关联案件并带入基本信息，保存后自动写入关联。
- 必填项：案件类型、案件名称、员工姓名、发生日期、承办人；员工工号与所属部门不再要求填写，部门由承办人所属部门自动带出。
- 案件描述改为选填；新增厂区（`plant_area` 字典，可搜索、可直接新增、可维护）、车间班组、小班长、大班长。
- 支持身份证号（AES 加密）、协办人/会签人/阅知人、附件上传。
- 建档即生成唯一编号（`MAX(seq)+1`）并初始化期限节点；保存草稿保持 `DRAFT`，提交立案流转 `FILED`。

#### 4.1.2 案件状态跟踪

- 按案件类型使用各自状态机，状态流转受 `CaseStateMachine.nextStatuses` 约束。
- 状态变更记录操作人、时间、前后状态、动作、意见；支持退回（`ROLLBACK`）。
- **自选节点流转**：推进时可在全部下游节点中任选（如立案直接到认定，跳过中间节点），退回时可选任一审级在前的节点（如争议处理退回立案）。可选目标由 `WorkflowFlowService.forwardTargets / rollbackTargets` 按当前拓扑计算，详情接口以 `forwardTargets / rollbackTargets` 下发；结案、归档不作为流转目标，草稿不可作为退回目标，仍各自走结案/归档动作。
- 节点可由「流程节点配置」动态调整，停用节点不参与流转。

#### 4.1.3 案件关联

- 工伤与仲裁案件可建立多对多关联；「争议关联」页按案件对去重展示，支持筛选、解除与 Excel 清单导出。
- 支持按案号搜索建立关联、解除关联，关联案件聚合展示。
- 关联/解除写审计日志。

#### 4.1.4 结案与归档

- 结案需审批权限（案件管理员/部门负责人/系统管理员），且状态机允许进入 `CLOSED`。
- 结案登记结案方式、卷宗页数、保管年限；结案时统一关闭该案件全部期限节点。
- 归档 `archive_status=1` 后只读，禁止编辑、推进、上传、分派。
- 归档库支持类型/年度/关键字检索与卷宗目录导出。
- 多级结案审批流与借阅审批为后续规划。

### 4.2 协同中心

#### 4.2.1 任务分派

- 承办人/负责人可在案件详情「任务」Tab 分派任务。
- 支持任务类型、责任人、截止时间、优先级、说明；完成后登记结果。
- 分派与完成写通知（站内信）与审计。

#### 4.2.2 待办中心

- 统一汇总三类待办：待办理任务（TASK）、待会签（COUNTERSIGN）、期限提醒（DEADLINE）。
- 超期置顶标红，显示超期天数；支持按类型筛选与跳转处理。
- 移动端 `/m/todos` 提供精简列表。

#### 4.2.3 会签

- 案件详情「会签」Tab 发起会签、记录意见（同意/不同意/有条件同意）。
- 会签记录生成待会签待办。
- 按比例/角色自动判定会签完成并驱动流转为后续规划。

### 4.3 文档中心

#### 4.3.1 证据材料管理

- 按案件管理材料，支持上传、预览、下载、删除（逻辑删除）。
- 单文件 ≤100MB，白名单 `pdf/doc/docx/xls/xlsx/ppt/pptx/jpg/jpeg/png/zip/rar`。
- 本地磁盘存储，`file_path` 存相对路径；预览/下载走鉴权接口。
- 归档案件禁止上传。

#### 4.3.2 文书模板

- 当前版本仅在详情页保留「生成文书」入口，提示当前节点应产出的材料。
- 模板维护、变量替换、自动归档为后续规划。

#### 4.3.3 版本管理

- 上传新版本生成递增版本号，历史版本可查看与下载。
- 版本链通过 `parent_id` 维护，文档逻辑删除。
- 版本对比与回滚为后续规划。

#### 4.3.4 权限与审计

- 按案件成员、敏感标识控制预览/下载，无权限返回 40301。
- 预览/下载写审计日志；前端不暴露物理路径。
- PDF 动态水印为后续规划（PDFBox 依赖已保留）。

### 4.4 期限中心

#### 4.4.1 法定/内部节点提醒

- 时限来源：流程节点配置（`wf_node_def.time_limit`，如「10 天」）；「视情况」「—」等非数值时限不设截止日期。
- 截止日期 = 进入节点当天 + 时限天数，按**工作日**推进（跳过周六、周日；当前未接入法定节假日日历）。
- 案件进入节点时自动生成该节点的期限记录（同案件同节点唯一；退回重办按本次进入日重算截止日期并重新打开），离开节点置 `DONE`。
- 提醒：截止日前 **7 个自然日**进入提醒窗口（`remind_days=7`）；距截止日**不足 7 天**状态显示「临近超期」，过截止日置 `OVERDUE` 并升级 `overdue_level`。
- 每日 08:00 定时扫描；页面支持「立即扫描」手动触发；通知写站内信。

#### 4.4.2 超期预警

- 超期节点在列表与看板标红，支持「仅看超期」。
- 支持登记超期原因、填写督办意见、手动完成。
- 结案时统一关闭全部期限节点，避免历史节点阻断结案。

### 4.5 报表中心

- 统计卡：案件总量、平均结案周期、任务完成率、期限超期率。
- 图表：月度建档趋势（近 12 个月）、案件类型分布、状态分布、金额统计（ECharts）。
- 导出《工伤事故人员信息统计表》Excel：标题、导出人/时间/人数留痕、11 列明细，仅统计工伤案件。
- 数据权限按角色过滤；导出写审计。
- PDF 导出与自定义报表为后续规划。

### 4.6 系统管理

#### 4.6.1 组织与用户

- 部门维护（新增/删除）、用户新增/编辑、角色分配、启用/停用、重置密码。
- 用户删除为软删除并进入回收站；拦截当前账号、内置 `admin`、最后一个管理员、在办案件承办人。

#### 4.6.2 RBAC 权限

- 8 个角色 + `data_scope`（ALL/DEPT/SELF）；菜单/按钮权限由 `sys_menu`/`sys_role_menu` 控制。
- 接口层结合 `@PreAuthorize` 与业务数据权限（本人/本部门/全部）。
- 字段级控制：身份证 AES 加密后脱敏；姓名按权限脱敏；金额按权限决定是否下发。
- 纯审计员不返回案件列表与业务明细。

#### 4.6.3 工作流与节点配置

- 自研状态机 `CaseStateMachine` 定义三大类型主链、分支与退回规则；`wf_node_def` 存储节点名称、时限、主责角色、关键材料、后继与启停。
- 节点可增删改、调序、启停；新增自动接链（前驱 → 新节点 → 原后继），删除由前驱接续后继；后继须同流程、不可自指、不可成环。
- 首末节点（草稿/归档）不可删除/停用；有在办案件或会使前驱无出路的节点不可停用。
- 节点变更写审计日志；流程版本管理与运行实例干预（转办/加签）为后续规划。

#### 4.6.4 审计日志

- 登录、查询、新增、修改、删除、流转、结案归档、文档访问、导出、权限变更、节点变更均写 `audit_log`。
- 支持关键字/模块/结果/时间检索，参数脱敏展示，保存≥3 年。
- ES 检索与导出为后续规划。

#### 4.6.5 消息通知

- 当前仅站内信（`channel=INNER`），支持未读数、单条/全部已读。
- 邮件与 IM 渠道为后续可选，字段已预留。

#### 7.1.1 日期参数格式（GET 查询）

- 查询参数中的日期统一使用 `yyyy-MM-dd`（如 `occurDateFrom=2026-11-03&occurDateTo=2026-11-21`），日期时间使用 `yyyy-MM-dd HH:mm:ss`；请求体中的日期由 Jackson 按同样格式解析。
- 服务端通过 `spring.mvc.format.date / time / date-time` 配置全局绑定格式；查询 DTO（`CaseQuery.occurDateFrom/occurDateTo`、`DeadlineQuery.dateFrom/dateTo`）的 `LocalDate` 字段再加 `@DateTimeFormat(iso = ISO.DATE)` 显式声明，避免 Spring 默认的本地化短日期解析导致 `Failed to convert property value` 绑定失败。
- 前端日期范围组件统一 `value-format="YYYY-MM-DD"`，清空筛选时传空串，后端按 `null` 处理。
- 格式非法的参数由全局异常处理器返回 `code=40001` 与可读提示（如「日期请用 yyyy-MM-dd」），不再输出 Spring 的转换异常栈。

## 8. 安全设计

### 8.1 权限模型

- **角色权限**：系统管理员、案件管理员、部门负责人、承办人、协办人、会签人、阅知人、审计员。
- **数据权限**：本人案件、本部门案件、全部案件。
- **字段级权限**：身份证号 AES 加密后脱敏、姓名按权限脱敏、金额按权限决定是否下发（明文存储，便于 SUM 统计）。
- **案件成员权限**：案件负责人拥有最高权限，承办人可编辑，协办人可查看并上传材料，会签人仅会签节点操作，阅知人只读。
- **功能权限（模块 × 操作）**：`sys_permission` 定义 13 个模块 37 个权限点（查看 / 新增 / 编辑 / 删除，以及导出、推进、批量导入等动作），`sys_role_permission` 维护角色授权；接口以 `@PreAuthorize("hasAuthority('模块:操作')")` 强制校验，登录时权限随 JWT `perms` 声明下发，前端按权限隐藏入口。
- **角色可维护**：内置 8 角色为预置模板，`/system/permissions` 支持自定义新建（`ROLE_CUSTOM_` 前缀）与删除；`ROLE_SYS_ADMIN` 禁止删除，删除时同步解除 `sys_user_role`、清理 `sys_role_permission`/`sys_role_menu` 并写审计。

### 8.2 审计留痕

- 登录、登出、查询、新增、修改、删除、审批、会签、下载、导出等操作全部记录审计日志。
- 默认写入本地审计日志表；启用 ES 时通过本地消息队列或异步任务写入供检索。
- 日志包含操作人、IP、时间、业务对象、操作前后关键数据（脱敏）。
- 保留策略：默认保留 1 年（`gsms.audit.retention-years` / `AUDIT_RETENTION_YEARS`），`AuditRetentionService` 每天 02:30 分批（1000 条/批）清理超期记录，服务启动时通过 `ApplicationReadyEvent` 异步补做一次。

### 8.3 文档安全

- 本地文件下载经后端鉴权后流式输出，前端不暴露物理路径。
- 预览/下载当前不添加动态水印（PDFBox 依赖保留，后续规划）。
- 敏感标识文档按角色限制下载；下载审批流为后续规划。
- 文档版本不可物理删除，仅逻辑删除。

### 8.4 传输与存储安全

- 全站 HTTPS；本地可使用企业内网 CA 或自签证书。
- 密码加盐哈希存储。
- 身份证号使用 AES-256-GCM 加密存储；金额为 decimal 明文存储，由接口层按权限控制下发。
- 本地数据库与文档目录定期备份，备份文件加密并存放于独立目录/介质。

### 8.5 CORS 与同源策略

- 前端统一由 Nginx 同源反代，正常情况下不涉及跨域；但浏览器对**同源 POST** 同样会携带 `Origin`，后端 CORS 过滤器会校验来源，不在白名单即返回 403。
- 规则：`gsms.web.allowed-origins` 精确白名单 + `allowed-origin-patterns` 网段通配（`127.0.0.1`、`localhost`、`[::1]`、`192.168.*`、`10.*`、`172.16-31.*`，端口不限）；`CorsConfigurationSource` 另按请求判断，`Origin` 的 host 与请求 `Host` 头一致即放行，覆盖更换 IP、域名或端口的场景。
- 前端使用 `Authorization: Bearer` 且 `allowCredentials=false`，放行同源/内网来源不存在 Cookie 被第三方站点利用的风险；外部站点来源仍返回 403。

### 9.1 部署架构

本机无 Docker，且 8GB 内存同时运行 Docker Desktop + MySQL + 应用余量不足，因此**采用 JAR + Nginx 的传统部署形态**。

- **生产/试用环境（即目标部署机）**：Windows 11 单机部署，`gsms-backend.jar` 以 `java -jar` 方式运行（可用 WinSW 注册为 Windows 服务），Nginx 托管前端 `web/dist` 并将 `/api` 反代到 8089，MySQL 8.0.45 使用本机实例，文档落 `E:/GSMS/data/files`。
- **开发环境**：IDE + Maven，连接本机 MySQL；前端 Vite dev server 代理后端。
- **测试环境**：与生产同机，使用独立库名与独立文件目录。
- **Docker Compose / Kubernetes**：仅作为后续迁移 Linux 的可选方案。

```text
客户端(Edge) ──HTTP/HTTPS──> Nginx(:8080/:8443)
                                ├── /            → E:/GSMS/web/dist  静态资源
                                └── /api         → 127.0.0.1:8089    gsms-backend.jar
                                                                       └── MySQL 127.0.0.1:3306
```

**开发机运行参数**：后端 8089、Nginx 8080、Vite 预览 4173；应用账号 `case_app`（仅 `case_system` 库权限）；JVM `-Xms512m -Xmx2g -Dfile.encoding=UTF-8`。

**生产服务器（192.168.11.179）**：Windows Server 2016 Standard、8C/16GB、仅 C 盘；JDK 1.8.0_231、MySQL 5.7.11（服务 `MYSQL57`，库 `case_system`）、Nginx 1.22；目录 `C:\GSMS\{backend,web\dist,nginx,data,sql,logs,backup}`；对外仅暴露 `8081`，后端 `8089` 仅本机监听；JVM `-Xms512m -Xmx1024m`。

```text
客户端 ──HTTP :8081──> Nginx(C:\GSMS\nginx)
                          ├── /        → C:/GSMS/web/dist
                          └── /api     → 127.0.0.1:8089  gsms-backend.jar（nssm 服务）
                                                             └── MySQL 127.0.0.1:3306
```

**推送模块（notify）**：`notify_config` / `notify_history` 两张表；`NotifyService` 统一负责预览与发送（所见即所得），`NotifyQueryMapper` 按「未结案 + 当前节点 + 未完成 + 距截止不足 N 天」筛选；`NotifyScheduler` 每分钟检查配置到期时间（cron `10 * * * * ?`），周期 DAILY/WEEKLY/MONTHLY；webhook 配置在表中，留空时取 `GSMS_NOTIFY_WEBHOOK`。预览接口基于表单参数即时计算，字段按勾选顺序渲染 PNG 图片。条件模型：`NotifyCondition`（field/op/value/values）以 JSON 存 `notify_config.conditions`，`ConditionFieldVO` 元数据驱动前端下拉，`NotifyQueryMapper.xml` 以白名单字段+操作符 choose 分支 + `#{}` 参数绑定构造动态 SQL（杜绝注入）；新增条件=元数据加一条+XML 加一个 choose 分支。内置 16 个字段，其中「是否已开启计时」按 `deadline_reminder.start_time` 是否为空判定（已开启/未开启）。鉴定休假天数 `case_injury_ext.rest_days` 已由 INT 调整为 `DECIMAL(6,1)`，支持 0.5 天等小数（V1.20）。

图片由 `NotifyImageRenderer`（Graphics2D，微软雅黑，22px 字号，开启抗锯齿/分数度量/高质量渲染）渲染为**表格样式**（表头+斑马纹+网格线，列顺序随字段勾选）。列宽按「表头与各单元格实测像素宽」自适应（单列 100–360px，案件名/部门/班组等长文本列放宽到 560px），图片宽度 = 列宽之和（最小 1120px、最大 2600px），字段越多图片越宽而非挤压；单格内容超出列宽时按像素**自动折行**，行高随行数增高（行高 = max(50, 行数×30+20)），因此不会再出现省略号截断。webhook 以 `msgtype=image`（base64 无换行 + md5）发送。`doPush` 在命中数为 0 时直接跳过不发送，历史标记 `SKIPPED`。

**工作日日历**：`WorkDayUtils` 启动时由 `WorkDayCalendarConfig` 注入 `gsms.calendar.holidays` / `gsms.calendar.makeup-workdays`（默认内置国务院 2026 年安排），可用环境变量 `GSMS_HOLIDAYS` / `GSMS_MAKEUP_WORKDAYS` 整体覆盖。`deadline_reminder.handle_date` 保存节点办理日期，进入节点默认当天，修改后由 `DeadlineService.adjustDeadline` 按工作日重算截止日期。

服务托管（nssm）：`GSMS-Backend`、`GSMS-Nginx` 均为自动启动的 Windows 服务；`GSMS-Backend` 依赖 `MYSQL57`，异常退出 5 秒后自动重启，日志落 `C:\GSMS\logs\backend.log`（10MB 轮转）。启停使用 `C:\GSMS\start-all.bat` / `stop-all.bat`，或 `sc start|stop GSMS-Backend`。

1. **确认基础环境**：`java -version`（1.8.0_391）、`mvn -v`、`sc query MySQL80`（Running）、`node -v`（22.x）、`netstat -ano | findstr :8080`（Nginx 已监听）。

4. **配置启动参数**（环境变量或启动命令）：
   ```text
   APP_PORT=8089

   DB_PASSWORD=<应用账号密码>
   JWT_SECRET=<32 字节以上随机串>
   CRYPTO_SECRET=<随机串>
   ```

   `CORS_ORIGIN_PATTERNS` 为内网来源通配：局域网通过 `http://<内网IP>:8080` 访问时浏览器仍会带 `Origin`，

### 9.4.1 生产服务器部署（Windows Server 2016）

1. **准备目录**：`C:\GSMS\{backend,web\dist,nginx,data\{files,tmp,logs},sql,backup,logs}`；Nginx 复用服务器已有安装并 `-p C:\GSMS\nginx` 指定前缀。
2. **导入数据库**：`mysql -uroot -p --default-character-set=utf8mb4 < init-mysql57.sql`（结构由开发库 `mysqldump --no-data` 生成，collation 统一为 `utf8mb4_unicode_ci`）；数据以业务库当前数据为准时，用 `deploy/remote/build_data_sync.py` 生成 `data-sync.sql` 覆盖导入，导入前先 `mysqldump` 备份。
3. **注册服务（nssm）**：`C:\partsportal\deploy\tools\nssm.exe`。
   ```bat
   nssm install GSMS-Backend "C:\Program Files\Java\jdk1.8.0_231\bin\java.exe"
   nssm set GSMS-Backend AppParameters "-Xms512m -Xmx1024m -Dfile.encoding=UTF-8 -Dgsms.storage.root=C:/GSMS/data/files -Dgsms.storage.temp=C:/GSMS/data/tmp -jar C:\GSMS\backend\gsms-backend.jar --spring.profiles.active=local --server.port=8089"
   nssm set GSMS-Backend AppDirectory C:\GSMS\backend
   nssm set GSMS-Backend AppEnvironmentExtra "STORAGE_ROOT=C:/GSMS/data/files" "STORAGE_TEMP=C:/GSMS/data/tmp"
   nssm set GSMS-Backend AppStdout C:\GSMS\logs\backend.log
   nssm set GSMS-Backend AppRotateFiles 1
   nssm set GSMS-Backend AppExit Default Restart
   nssm set GSMS-Backend Start SERVICE_AUTO_START
   sc config GSMS-Backend depend= MYSQL57
   ```
   > 实测注意：`nssm set AppParameters` 传长参数可能被清空，`AppEnvironmentExtra` 经 CLI 设置也可能不落盘；稳妥做法是直接写注册表 `HKLM\SYSTEM\CurrentControlSet\Services\GSMS-Backend\Parameters` 的 `AppParameters`(REG_SZ) 与 `AppEnvironmentExtra`(REG_MULTI_SZ)，同时在启动参数里用 `-Dgsms.storage.root` 兜底。
4. **Nginx**：`server` 监听 8081、`root C:/GSMS/web/dist`、`try_files $uri $uri/ /index.html`、`/api` 反代 `127.0.0.1:8089`、`client_max_body_size 100m`；`error_log` 用相对路径（绝对路径会导致启动即退出）。360 等安全软件会查杀手工启动的 `nginx.exe`，须以服务方式运行。
5. **防火墙**：仅放行 8081（`New-NetFirewallRule -DisplayName 'GSMS-8081' -Direction Inbound -Protocol TCP -LocalPort 8081 -Action Allow`）。
6. **验证**：`/actuator/health` 为 `UP`、`http://192.168.11.179:8081/` 返回 200、登录拿到 token、`/api/v1/cases` 返回数据。

### 9.5 备份与恢复

- 每日 02:00 通过 Windows 任务计划程序备份 MySQL 与文档目录，输出至 `E:\GSMS\data\backup`：
  ```bat
  "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysqldump.exe" -u case_app -p^<密码^> ^
    --single-transaction --routines --triggers --default-character-set=utf8mb4 ^
  ```

- 文档目录按周打包 `E:\GSMS\data\files` 与 `application-local.yml`（含密钥，单独加密存放）。

- 每季度至少执行一次恢复演练并留存记录，演练使用独立库名 `case_system_restore`，不覆盖生产库。

## 12. 附录

### 12.1 工伤案件状态机（简）

```text
草稿(DRAFT) → 立案(FILED) → 调查取证(INVESTIGATION) → 申报(DECLARE)
→ 认定(RECOGNITION) → 鉴定(APPRAISAL) → 待遇处理(TREATMENT)
→ 争议处理(DISPUTE) → 结案(CLOSED) → 归档(ARCHIVED)
```

- `TREATMENT → CLOSED` 为无争议直接结案分支。
- 推进与退回均可自选目标节点：推进可选任一可达下游节点（跳过中间节点），退回可选任一上游节点；跳级时被跳过节点的期限自动置为已完成，退回时途经节点的期限重新打开。归档不可退回。
- 认定、鉴定、待遇处理支持会签记录。

### 12.2 劳动仲裁案件状态机（简）

```text
草稿(DRAFT) → 立案(FILED) → 证据准备(EVIDENCE) → 开庭(HEARING)
→ 裁决(AWARD) / 调解(MEDIATION)
→ 履行(PERFORM) → 结案(CLOSED) → 归档(ARCHIVED)

上诉分支：裁决(AWARD) → 上诉(APPEAL) → 开庭（二审）(RETRIAL_HEARING) → 裁定(RULING) → 履行(PERFORM) → 结案(CLOSED)
```

- 开庭后按结果分支至裁决或调解；裁决后可履行或上诉；裁定后同样必须进入履行，履行完毕才能结案。
- 调解可直接进入履行或结案。
- 履行节点可登记履行状态与完成日期。
